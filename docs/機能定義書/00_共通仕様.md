# 機能定義書 - 共通仕様

[← 機能一覧に戻る](../機能一覧.md)

全機能の機能定義書に共通する決まりをまとめる。

## 1. 機能定義書の書き方

各機能定義書は、次の項目で書く。

| 項目 | 内容 |
|---|---|
| 概要 | その機能で何ができるか |
| アクター・前提条件 | 誰が使うか、使う前にどうなっている必要があるか |
| 対象画面 | 画面ID（[画面設計](../画面設計.md)） |
| 入力項目 | 項目・必須・ルール |
| 処理の流れ | 画面・API・DB のやり取り（Mermaid のシーケンス図） |
| 業務ルール | その機能で守るべき決まり |
| API | メソッド・パス・リクエスト・レスポンス |
| エラー | どんなときに、どのステータスで、何を表示するか |
| 使用テーブル | [ER図](../ER図.md) のどのテーブルを読む・書くか |

## 2. API の共通ルール

- パラメーター・リクエスト・レスポンスの項目の正確な形は、コードから自動で作る API 仕様書 [docs/api/openapi.yaml](../api/openapi.yaml) を見る（Swagger UI：開発中に http://localhost:8081/swagger-ui.html）。機能定義書には、業務ルール・画面の動き・エラーの文言など「なぜそう動くか」を書く
- パスはすべて `/api` から始める
- すべてのレスポンスに、リクエストごとの ID を `X-Request-Id` ヘッダーで返す（サーバーのログの `request_id` と同じ値。問い合わせのとき、ログを特定するのに使う。[ログ・監視設計](../ログ・監視設計.md)）
- リクエストとレスポンスは JSON（画像を送る投稿作成だけ `multipart/form-data`）
- 日時は ISO 8601 形式・UTC で返す（例：`2026-09-26T11:30:00Z`）。「3分前」などの表示への変換はフロントエンドで行う
- ユーザーを指すパスには、id ではなく @ユーザーID（`username`）を使う（例：`/api/users/taro_dev`）。画面の URL（`/users/taro_dev`）と対応させるため
- ログインが必要な API をログインせずに呼んだら `401 Unauthorized` を返す（ログインしなくても呼べるのは `GET /api/auth/csrf`・`POST /api/auth/signup`・`POST /api/auth/login`・`POST /api/auth/refresh`・`POST /api/auth/logout` だけ）
- ログイン状態は JWT のアクセストークン（15分）とリフレッシュトークン（7日）で持つ。どちらも HttpOnly Cookie なので、ブラウザが自動で送る。画面側でトークンを読んだり保存したりする必要はない（詳しくは [F-02](./F-02_ログイン・ログアウト.md)）
- API が 401 を返したら、画面は `POST /api/auth/refresh` を1回だけ呼び、成功したら元の API を呼び直す。refresh も 401 ならログイン画面へ移動する
- **CSRF 対策**：`GET` 以外（`POST`・`PUT`・`PATCH`・`DELETE`）には、`XSRF-TOKEN` Cookie の値を `X-XSRF-TOKEN` ヘッダーに入れて送る。無い・正しくないときは `403 Forbidden`。**ログイン中でも同じ**（トークンを Cookie で渡しているため、ログイン中のリクエストこそ別サイトから勝手に送られる危険がある）
  - 画面を開いたら最初に `GET /api/auth/csrf` を呼んで Cookie を受け取る
  - ログイン・新規登録の成功時にトークンが新しくなる（`Set-Cookie` で届く）。毎回 Cookie から読み直して送る

## 3. エラーレスポンスの形式

```json
{
  "code": "VALIDATION_ERROR",
  "message": "入力内容に誤りがあります",
  "errors": [
    { "field": "email", "message": "このメールアドレスはすでに登録されています" }
  ]
}
```

| ステータス | code | 使う場面 |
|---|---|---|
| 400 Bad Request | `VALIDATION_ERROR` | 入力チェックに失敗した。`errors` に項目ごとのメッセージを入れる |
| 401 Unauthorized | `UNAUTHORIZED` | ログインしていない、またはログインに失敗した |
| 403 Forbidden | `FORBIDDEN` | 権限がない操作をした（他人の投稿を編集・削除しようとした など） |
| 404 Not Found | `NOT_FOUND` | 投稿やユーザーが存在しない |
| 409 Conflict | `CONFLICT` | メールアドレスや @ユーザーID がすでに使われている |
| 413 Payload Too Large | `PAYLOAD_TOO_LARGE` | 画像のサイズが大きすぎる |
| 429 Too Many Requests | `TOO_MANY_REQUESTS` | ログインの失敗が続いた（F-02 の総当たり対策） |
| 500 Internal Server Error | `INTERNAL_ERROR` | サーバー側の想定外のエラー |

## 4. ページング

タイムライン・投稿一覧・コメント一覧・検索結果は、1回に20件ずつ返す。

- 「前回の最後の id より古いもの」を取る**カーソル方式**にする（`?before={id}`）
- ページ番号方式（`?page=2`）にしないのは、読んでいる間に新しい投稿が増えると、次のページで同じ投稿が重複して出てしまうため

```json
{
  "items": [ ... ],
  "nextCursor": 1234
}
```

- `nextCursor` が `null` なら、それ以上データはない

## 5. 投稿の共通レスポンス（PostResponse）

タイムライン（F-03）・投稿作成（F-04）・投稿詳細（F-05）・ユーザーページ（F-08）・投稿編集（F-10）で同じ形を使う。

```json
{
  "id": 1234,
  "body": "Spring BootでAPIを作ってみた！",
  "createdAt": "2026-09-26T11:30:00Z",
  "editedAt": null,
  "author": { "username": "taro_dev", "name": "山田太郎", "avatarUrl": null },
  "images": [
    { "id": 501, "url": "https://example.com/images/posts/1234/3f2a....jpg", "position": 1 }
  ],
  "likeCount": 12,
  "commentCount": 3,
  "likedByMe": true,
  "isMine": false
}
```

- `editedAt`：最後に編集した日時。編集していなければ `null`。値があれば「編集済み」と表示する（F-10）
- `images[].id`：投稿編集で「残す画像」を指定するときに使う（F-10）
- `likedByMe`：ログイン中のユーザーがいいね済みかどうか。いいねボタンの見た目の切り替えに使う
- `likeCount`・`commentCount`：いいね数・コメント数。表示するたびに数える（タイムラインでは20件分を1回の SQL でまとめて数え、N+1 問題を避ける）
- `isMine`：ログイン中のユーザーの投稿かどうか。`true` のときだけ「…」メニュー（編集・削除）を出す。**画面の表示を切り替えるためだけのもの**で、編集・削除の API では必ずサーバー側で投稿者を確認する
- `author.avatarUrl`：投稿者のプロフィール画像の URL（F-12）。設定していなければ `null`（画面は名前の1文字目の丸を出す）。コメント（F-05）の `author` も同じ形
- インプレッション数・リツイート数の項目は**持たない**

## 6. ユーザーの共通レスポンス（UserSummary）

検索結果（F-09）などで使う。

```json
{
  "username": "taro_dev",
  "name": "山田太郎",
  "avatarUrl": null,
  "followedByMe": false,
  "isMe": false
}
```

- `avatarUrl`：プロフィール画像の URL（F-12）。設定していなければ `null`
- `isMe`：ログイン中のユーザー自身か。`true` ならフォローボタンの代わりに「あなた」と表示する
